## Architecture

Next.js 16 App Router, TypeScript.

**Data flow:** `BirthForm` → `/api/geocode` + `/api/timezone` → `/api/calculate` → `DualChartData` → the dossier (`DossierHeader` + `FrameControl` + `FrameShiftWheel` + `ReadoutRail` + `ReadingPanel`) → `/api/reading` (sequential streaming, one per planet section). Synastry adds a parallel flow: two births → `/api/synastry` → inter-aspects + composite → `SynastryAspectsPanel` + `SynastryReadingPanel`.

Page routes: `/` (main app), `/method`, `/guides`, `/sample`, `/synastry`.

### API routes

- **`/api/calculate`** (`maxDuration=30`): validates birth data (16 KB payload guard), rate-limited (30 req/60s), derives DST-accurate UTC offset via `Intl.DateTimeFormat`, fetches Pluto from JPL Horizons DE440 (5s timeout, falls back to local Meeus), calls `calculateDualChart()`. Returns `DualChartData` with `plutoSource`.
- **`/api/synastry`** (`maxDuration=30`): rate-limited (20 req/60s, 16 KB guard), computes two natal charts, inter-aspects, and a midpoint composite chart via `synastry-calc.ts`.
- **`/api/geocode`**: Nominatim proxy. 200-char query limit, rate-limited (30 req/60s per IP), one app-wide 1 req/s gate to Nominatim (`axis:rl:nominatim:global`), results cached in Redis for 30 days, field-whitelisted. Nominatim's usage policy forbids autocomplete, so `BirthForm` searches only on Enter or its SEARCH button — never on a keystroke timer.
- **`/api/timezone`**: GET `?lat=&lon=` → `{ tzName }`. Uses `tz-lookup` (offline, no external calls). Rate-limited (60 req/60s).
- **`/api/reading`** (`maxDuration=120`): ⚠ **v10.41 — the section is BUFFERED and deterministically pre-flighted before the reader sees a character of it** (`lib/reading-preflight.ts`). The gate runs under `after()`, which is right for the LLM evaluator and wrong for everything else, and it produced the product's oddest property: the FIRST reader of an uncached section got ungated prose and every reader after them got the better text, so first impressions landed on the worst version the pipeline makes. Synchronous gating was measured and rejected (`scripts/time-gate.test.ts`) — generate + evaluate + repair does not fit `maxDuration` and an overrun costs the reader the section entirely. But the gate is two things wearing one name: the evaluator is slow, expensive and nondeterministic, while `scoreLength`, `detectBannedOpeners`, `antithesisTicExceeded`, `detectRescuePhrasings`, `scanSectionRules` and `checkNumericFacts` are pure, make no model calls and run in microseconds — `reading-rule-scan.ts` had said so in its own header the whole time ("unlike the LLM gate it *could* run on the hot path"). So the route generates, buffers, runs every deterministic check, and on a **hard** finding regenerates ONCE with the faults named, serving whichever attempt has strictly fewer findings (`pickBetter`; a tie keeps the first pass, which was written without a correction hanging over it). Cost: one extra generation **only on the sections that trip**, versus the evaluator's one call on every section whether it trips or not. Only a hard length miss regenerates — merely out-of-band scores 3 and the gate does not fail it either, so chasing it would spend a call for nothing. Truncated output is excluded, since regenerating hits the same token ceiling. The rewrite turn carries the faults and **not** the failed draft, which is the v10.40 repair lesson applied: the faults are string facts, so naming them is the whole message. ⚠ **THE TRADEOFF**: the section no longer streams token-by-token — roughly 15–25s of blank where tokens used to appear. It is affordable for every section but the first, because `ReadingPanel` fires the whole chain as fast as the API serves it (~5–9 minutes of generation against ~36 minutes of reading), so the pipeline runs minutes ahead of the reader; the opening section has no such cover and pays it in full, which is why `ReadingPanel` states plainly that each section is written in full and checked before it is shown. `AXIS_PREFLIGHT_ENABLED=false` is the kill switch. ⚠ **`AXIS_INLINE_GATE=true` (default OFF) additionally gates a NON-OPENING section inline**, so the repair reaches the first reader too, paid out of the time they spend on earlier sections; it serves exactly what it caches, and `gatedInline` stops `after()` paying for the same evaluation twice. **It should stay off until `maxDuration` is raised**: worst case inline is generate + pre-flight rewrite + evaluate + repair + re-score ≈ 135s against a 120s ceiling, and an overrun costs the reader the whole section — strictly worse than today's failure mode, which is merely ungated prose. `INLINE_GATE_DEADLINE_MS` (35s from the top of the handler) makes it degrade safely rather than make it fit: with no budget, on an error, or on a verdict with nothing to cache, the first pass is served and `after()` runs the gate exactly as before. `[AXIS_PREFLIGHT]` and `[AXIS_INLINE_GATE]` log one line each in the `[AXIS_*]` family, and `preflight-rewrite` is a `ModelCallKind` so the extra generation shows in `[AXIS_USAGE]`. ⚠ `[AXIS_LEN]` measures the word count the GENERATOR produced, captured before the inline gate can replace the text. Rate-limited (20 req/60s, Redis-backed), validates section/planetSection against allow-lists, recomputes chart server-side from birth data (no client-trusted positions), checks Redis cache, calls `buildInterpretationContext()` + `formatEliteChartBlock()`, renders the section instruction through `renderSectionInstruction()` (which substitutes the length clause from the band *this chart* will be scored against — see prompts.ts), and streams the Claude response straight through to close. A mid-stream generation failure is classified and reported in-band via `reading-stream.ts` (see below), never as a status code — the response headers are already sent by then. Generation model: `claude-sonnet-5`. Quality evaluation uses `claude-sonnet-5-5` (exported as `EVAL_MODEL`); repair and doctrine-repair run on the caller's generation model, Sonnet 5. **Sonnet 5 / Opus 5 REMOVED the sampling params — sending `temperature` (or `top_p`/`top_k`) returns a 400 and fails the call, so there is no temperature knob (`AXIS_READING_TEMPERATURE` is gone); do not re-add one.** ⚠ As of v10.30 the thinking config is **no longer uniform**. The generation and repair calls still pass `thinking: { type: 'disabled' }` — these models otherwise default to adaptive thinking, whose tokens count against `max_tokens` (truncating the per-section prose budget) and add first-token latency across the ~21 sequential sections, and a repair is a constrained rewrite against an explicit critique rather than a judgment call. The **evaluator** passes `thinking: { type: 'adaptive' }` with `output_config: { effort: 'medium' }` and `EVAL_MAX_TOKENS` raised 1200 → 4000 (adaptive thinking tokens come out of `max_tokens`, so a JSON-only budget would truncate the scores object the moment the model thought at all). Why the evaluator is the exception: it runs under `after()`, entirely off the response path, so reasoning costs the reader no latency — the latency argument that justifies no-thinking on the generator does not apply to it at all — while scoring nine prose criteria and emitting strict JSON is precisely the task reasoning helps most. The former pairing (Opus 5 with thinking disabled) was the worst of both: Opus input bills at 2.5× Sonnet over roughly the SAME token volume the generation call pays, making **evaluation the larger half of the bill** for a benefit the first reader never sees, while the judgment it was bought for was switched off. Note `thinking: {type:'disabled'}` is a **400** on `claude-sonnet-5-5`, so the split is enforced by the API, not just by preference. **When birth time is unknown, the dedicated `ascendant`/`lagna` section is not sent to the model at all** — the angle is uniform across the zodiac at noon, so the route returns a short deterministic explainer instead (free; no model call, no rate-limit spend); every other section still runs, since sign-based placements are accurate without a birth time. **The LLM quality gate runs as evaluate-and-recache**: the stream closes first, then `gateForCache()` runs via `after()` (from `next/server`) while the invocation is still alive, so gating adds **zero latency to the reader** — `after()` (not bare post-`close()` code) is what guarantees the platform keeps the instance alive to finish it, so the cache write and the spend count are not dropped when the response flushes and decides only what lands in the cache. Consequence to keep in mind: the *first* reader of an uncached section sees ungated first-pass prose; every reader after them is served the gated (and where it failed, repaired) text. Every gate call carries a request timeout that expires at `GATE_HARD_DEADLINE_MS` (112s from the top of the handler) with SDK retries off, so a slow call cannot run past `maxDuration`; and each call is recorded against the daily cap the moment it is made (`gateForCache`'s `onModelCall`), with any remainder recorded at the end — recording only a final total lost every call made before an overrunning invocation was killed. When the gate cannot confirm a section (repair failed its re-score, repair errored or came back unusable, no budget left to repair) it returns `provisionalText`, the doctrine-clean first pass, and the route caches it for `PROVISIONAL_TTL_SECONDS` (24h) instead of not at all: uncached, every later view of the chart regenerated and re-gated it at ~4 calls per view, indefinitely. Truncated or doctrine-breaching text is never cached, provisionally or otherwise. Cost per uncached section is 1 model call (generate) + 1 (evaluate), + 1 more when only a doctrine hit fails (the 500-token surgical edit, not re-scored), or + 2 more when a full repair fires (the repair itself + a re-score of the repair) — all counted through `recordModelCalls` against the daily cap. The generation call is **reserved as it is made** (the write is fired, deliberately NOT awaited — it is the reader's critical path — and flushed under `after()` on both the success and the failure exit); only the gate's calls are recorded from inside `after()`. Recording the whole count post-gate left the counter trailing real spend by the full gate duration (~30–60s), so concurrent traffic could run past the cap by the number of requests in flight, and a generation that failed after billing went uncounted entirely. The counter now bounds calls *started*, which is what the cap is for; a reservation is never refunded (`reading-route-budget.test.ts`). **Per full reading**, with every section uncached: a natal reading is 21 sections (9 Tropical + 8 Sidereal + 4 Divergence; 19 when birth time is unknown, since `ascendant`/`lagna` are free), so **42 calls minimum** (generate + evaluate on every section) and **up to 84** if every section takes a full repair; synastry is 6 sections, 12–24 calls. The call COUNT is unchanged by v10.30; what changed is the price of the evaluate/recheck half of it (Opus 5 → Sonnet 5.5, $5/$25 → $2/$10 per MTok) and the volume every call carries (the v10.30 length reset cut the natal reading ~28%, and because prior sections are resent verbatim on every later section, each word cut is a word removed from up to twenty subsequent prompts on BOTH the generation and the evaluation call — ⚠ **v10.36 reversed that cut**, for the reasons under *Per-section-type targets* below, so the volume term is back to roughly its pre-v10.30 level; the compounding mechanism this describes is unchanged and is why length is still the cost term to watch). A cache hit costs 0 calls, and `AXIS_GATE_ENABLED=false` drops a section to 1. The real per-reading figure, with token counts and list-price cost, comes from the `[AXIS_USAGE]` lines or `npm run eval`'s `summary.json` — no repair rate is assumed here. `AXIS_GATE_ENABLED=false` disables gating without a redeploy (mirrors `AXIS_READINGS_ENABLED`), falling back to caching only a clean, non-truncated first pass. Wall-clock guards in `gateForCache` measure from the top of the handler: no eval starts after 95s elapsed, no repair after 70s — overrunning costs the cache write, never the reader's section. Cache-write guards are the `truncated` stop_reason flag, `isTruncated()`, and the deterministic banned-phrase scan (`detectBannedPhrasings`, now in `reading-quality-gate.ts`). The scan runs in two passes: **literal** (`BANNED_HIERARCHY_PHRASINGS` + `BANNED_RESCUE_PHRASINGS`, substring-matched — every entry is a construction with no innocent use) and **contextual** (`detectContextualHierarchy`, for ordinary words like "underneath"/"beneath"/"the mask" that only breach THE LAW within `HIERARCHY_PROXIMITY_CHARS` of identity/system language). Keep bare ordinary words OUT of the literal list — a false positive now sends a clean section through a needless repair pass. A doctrine hit is no longer a bare cache veto. When the evaluator otherwise approves the section, the gate sends only the offending sentence(s) through a 500-token surgical edit and splices the replacements into the original byte-for-byte; this avoids paying for or risking regression across a full-section rewrite. If the prose rubric also fails, the ordinary full repair still addresses both failures. Gate outcomes log one greppable `[AXIS_GATE] section=… reason=… <per-criterion scores>` line per gated section — the only production visibility into the score distribution. Every model call the route makes — the generation and each gate call — logs one `[AXIS_USAGE] section=… call=generate|evaluate|recheck|repair|doctrine-repair model=… in=… cache_read=… cache_write=… out=… stop=…` line (`lib/usage-log.ts`) from the API's own `usage`; the generation line adds `prior=<sections already read>`. It is the only production record of what a reading costs and whether prompt caching is landing (a section after the first should show a large `cache_read` and a small `in`).

Planet sections — **tropical**: sun, moon, ascendant, mercury, venus, mars, jupiter_saturn, key_aspects, rahu_ketu · **sidereal**: lagna, sun, moon, mercury, venus, mars, jupiter_saturn, rahu_ketu · **synthesis** (The Divergence): agree, diverge, tension, closing · **synastry**: luminaries, venus_mars, outer_planets, composite_chart, central_dynamic, navigation

- **`lib/interpretation-engine.ts` — `buildDivergencePlan(DualChartData)`**: the single deterministic evidence base for all four Divergence sections (`formatSynthesisBlock` renders it; the route sends NOTHING else for `synthesis`, so a fact absent from the plan is a fact the model does not have). Walks all twelve bodies plus both angles in both frames, carrying degree, dignity, retrogradation, sidereal nakshatra and sign-ruler condition. **Concordance has two grades** — full (sign + dignity + house) and SAME-SIGN (sign + dignity, house moves). The second grade is load-bearing, not a technicality: AXIS uses Whole Sign houses, so when the Ascendant shifts sign under the ayanamsa — which it does on most charts — every same-sign body ALSO renumbers house. Requiring the house to match made concordance structurally unreachable and left the `agree` section with no allocated evidence on ~75% of charts. Divergences are ranked by `structural` (size of the shift: sign 4, dignity 3, house 2, Ascendant 9 because a Lagna shift renumbers every house) plus `DIVERGENCE_BODY_WEIGHT` (luminaries and angles > personal planets and the nodes > outers) — the ranking rule that used to be prose in the diverge prompt, moved here because ranking from chart facts is deterministic and a prompt-side instruction cannot be verified. Candidates at or above `STRUCTURAL_CUTOFF` are worked in depth (max 4, **no minimum** — the chart decides); the rest land in `remaining`, which the diverge prompt names in one compressed clause as THE LAW requires. ⚠ `SIGN_RULERS_VEDIC` is a copy of `SIGN_RULERS_TRADITIONAL`, so the sign ruler is NEVER system-specific — a changed ruler is a consequence of the changed sign and must not be scored or described as the systems disagreeing about rulership. What IS independent evidence is the dispositor's own *condition* differing.
- **`lib/synastry-calc.ts`**: computes inter-chart aspects (orb-limited, 5 major aspects) between two natal charts and a midpoint composite chart. Unlike the rescue clamp it is applied BEFORE `rubricPass` is computed, because `rubricPass` routes a doctrine-only failure to the surgical sentence edit, which cannot fix an opening — applied after, a section with both a doctrine hit and a banned opener would be spliced and cached with the opener intact. An opener hit never vetoes a cache write on its own (gate disabled / eval skipped): it is a style fault, and an uncached section costs a model call on every page load. The **antithesis tic** has a third deterministic backstop, added v10.34: `antithesisTicExceeded(text)` (exported from `reading-rule-scan.ts`, so the gate clamps on the SAME detector the scan reports and a second copy of those regexes cannot drift) clamps `voice_quality` below `MIN_INDIVIDUAL` when the contrastive construction passes PART 4's one-per-section cap, and prepends an ANTITHESIS-TIC FAILURE critique naming the count and every instance. Applied BEFORE `rubricPass` for the same reason as the opener: the doctrine-only route splices individual sentences, and a construction repeated across paragraphs is not a sentence-level fault, so a spliced section would be cached with the tic intact. Why it is deterministic rather than left to the rubric: on the 2026-11-03 eval run the evaluator cited this tic unprompted in **11 of 21** critiques and the scan independently counted 15 instances, but the scan's finding was `soft` and fed nothing, so it reached a repair only when the rater happened to write about it and the other ten sections shipped it. The count is a string fact about the output and should not depend on a judgment call. The rescue clause additionally has a deterministic backstop, `detectRescuePhrasings(text)`: a literal case-insensitive match on the curated high-precision `BANNED_RESCUE_PHRASINGS` forces `contradiction_handling` below `MIN_INDIVIDUAL`, so the flattery is repaired even when the evaluator missed it (the softer, context-dependent cases the list omits are left to the LLM criterion's deletion test). The banned-Barnum phrasings are a shared const (`BANNED_BARNUM_PHRASINGS`/`BANNED_BARNUM_LIST` in `prompts.ts`) imported by both files so prompt and gate cannot drift; `FALSIFIABILITY_DIVERGENCE_EXAMPLE` is the permanent regression fixture proving `specificity` and `falsifiability` are orthogonal. **Truncation is a pre-scoring hard failure**: `isTruncated(text)` (truncation sentinel present, or prose ending on a non-terminal char) short-circuits `evaluateSection` to `{ pass:false, scores:null, truncated:true }` with no eval call. `gateForCache` checks it alongside the generation's own `stop_reason === 'max_tokens'` flag, which the route passes in as `truncated` and which is authoritative where the heuristic is not (a section cut at the token ceiling can still happen to end on a full stop). Truncated text is never scored, never repaired in place, and never cached.
- **`lib/reading-thread.ts`** + **`lib/reading-order.ts`**: the reading thread that makes a natal reading one continuous document. `reading-order.ts` (client-safe) holds `NATAL_SECTION_ORDER` and `priorSectionsFor` — every section the reader has read before a given one (all of each earlier frame, then this frame's earlier sections). `ReadingPanel` opens a thread per cast chart (a UUID `threadId` in every `/api/reading` body); the route loads the earlier sections (`loadPriorSections`), sends them as one content block per section ahead of the chart context (identical blocks across requests, cache breakpoint on the last, so prompt caching reuses all but the newest), and stores this section's text (`storeThreadSection`) **before** closing the stream, because the client fires the next section the instant this one ends. Stored text is what the reader saw (first pass, cached text, or the unknown-time notice), never the gate's later repair. The server holds the text, never the client: the 16 KB payload guard would reject it by the fifth section, and client-supplied text would be a prompt-injection and cache-poisoning path. The thread key binds the id to the chart's birth data; entries expire after 24h (Redis, with a per-instance in-memory fallback). `priorDigest` is folded into the reading cache key, and as of v10.29 it digests **which** earlier sections preceded this one, in order — deliberately not their prose; an unthreaded request is an opening section. It used to digest the text, which quietly destroyed the cache: the route threads the FIRST PASS (continuity is with what was read) while the gate caches the REPAIRED text, so the next reader of the same chart was served `T1′`, threaded `T1′`, and computed a different key for section 2 than section 2 was cached under. The chain forked at the first repaired section and never rejoined — reusable only for the maximal prefix of sections the gate did not repair (expected `(1-r)/r` of 21 at repair rate `r`; about 4 at r=0.2), with every later section regenerated for every reader forever, including the same person reloading their own dossier, and every miss writing a row under a digest nobody would ever produce again. Keyed on the section list, every reader of a chart computes the same key at every section. What is given up: a cached section may have followed the first-pass wording of an earlier section while this reader saw the repaired wording — a repair of the same section, not a different one. A section the thread is missing (failed, expired) is absent from the list and so changes the digest, which is correct: that reading genuinely had different material before it. The gate gets the same prior blocks (`priorSectionBlocks`, not a flattened string) so its evaluator and repair calls read the reading so far from the prompt cache; its evaluator scores repetition across the reading. Synastry is not threaded. `phrasesAlreadyUsed` / `overusedTics` (rendered by `phrasesAlreadyUsedBlock`, placed ahead of the section instruction) name the refrains the reading so far already leans on — 2–4-word phrases repeated ≥3 times across ≥2 sections, headings and chart vocabulary excluded, plus counted verbal tics such as the "rather than" antithesis — so the next section is told by name not to reuse them. ONE CONTINUOUS READING also bans contradicting an earlier behavioural claim without naming the condition under which each holds.
- **`lib/reading-stream.ts`**: both halves of `/api/reading`'s in-band failure protocol, kept in one file so they cannot drift. A generation failure cannot be an HTTP status — by the time the model call fails the streaming `Response` has already gone out with a 200 — so the route writes a sentinel into the body instead. `classifyGenerationError(err)` (server) splits failures into **fatal** (the *account* is the problem: an exhausted credit balance, which Anthropic reports as a **400 `invalid_request_error`** and not a 402, so the message must be read and not just the status; plus 401/403 auth) and **transient** (overload, 5xx, network). `detectStreamError(text)` (client) reads the sentinel back: `[AXIS_STREAM_ERROR: generation failed]` stays retryable, `[AXIS_STREAM_ERROR: unavailable:<code>]` is fatal and makes the panel throw `ReadingUnavailableError` to unwind the whole run. Why this exists: a natal chart fans out to ~21 sections and each panel retries once, so treating a fatal failure as retryable turns **one** exhausted balance into ~42 doomed API round trips while telling the reader "please retry" for something no retry can fix. An unknown future `unavailable:` code stays fatal by design. Server-side each failure logs one greppable `[AXIS_GEN_FAIL] section=… fatal=… code=…` line.
- **`lib/reading-rule-scan.ts`**: the deterministic compliance scan for the `SHARED_RULES`/`DOCTRINE.md` constraints that are pure string facts about finished prose. **Why it exists:** before v10.30 the pipeline had exactly five deterministic checks on generated prose (`scoreLength`, `isTruncated`, `detectRescuePhrasings`, `detectBannedOpeners`, `detectBannedPhrasings`); everything else was either advisory rubric prose handed to the LLM evaluator or unchecked. That left the rules whose violations a reader notices *immediately* and which are trivially checkable in code with **zero enforcement anywhere** — no prescriptions ("you should", "work on"), no predictions ("you will", "this will bring"), British spelling, no bullet points, 3–4-sentence paragraphs, no greetings/sign-offs, and THE SMOKE DETECTOR word list against generated prose. The engineering budget had gone to an LLM judge for the hard, subjective 20% while the trivially automatable 80% was guarded only by a prohibition ~11,000 tokens upstream of the output. `scanSectionRules(text)` returns `RuleFinding[]` (`rule`, `severity`, `match`, `line`); `summariseRuleScan` aggregates; `formatRuleScanLog` emits one `[AXIS_RULES] section=… hard=… doctrine=… soft=…` line in the `[AXIS_*]` family. Three severities: **`hard`** = unambiguous breach of a stated rule, **`doctrine`** = a THE SMOKE DETECTOR or claim-level LAW candidate (DOCTRINE is explicit that the grep finds candidates and THE LAW decides, so these are reported for audit, never asserted as failures), **`soft`** = a breach only in aggregate (one long paragraph is a slip, six is a pattern; `antithesis-tic` — added v10.31 — reports ONE finding per section once "rather than" / "not X but Y" / "less a X than" passes the one-per-section cap, carrying the count, and is scoped to keep bare "rather", concessions, "not only…but" and ordinary comparatives silent). ⚠ **False positives are the design constraint**, because a scanner that cries wolf gets switched off: prescriptions/predictions match only SECOND-PERSON constructions (bare "consider" and "will" are ordinary English — "the pattern will often surface" is the hedged form the prompt actually requires), the smoke-detector terms are sentence-scoped and fire only alongside inter-system language (so the conjunction's "Merger" and Scorpio's "merger through depth" stay silent), and British spelling uses a closed list of the exact pairs the prompt names rather than an `-ize`/`-our` heuristic (so "size", "prize", "glamour", "hour" are safe). ⚠ v10.38 narrowed the `prescription` check: "should"/"ought to" match anywhere, but "need to"/"must"/"have to" are ALSO ordinary descriptive English inside a clause introduced by a subordinating conjunction, and the v10.37 run reported "a conversation that gives you room to draft **before you have to speak**" as a hard breach. A temporal clause is not advice, and a hard breach is the loudest thing this file can say, so the conditional modals now carry a negative lookbehind for before/until/when/whenever/while/if/once/unless/after/as/where/than. ⚠ v10.35 added `register-drift` (`hasRegisterDrift`/`registerFor`), the PART 4 second-person check: a natal section containing NO second-person pronoun at all is `hard`. It is **frame-aware and fails closed** — The Divergence is third person by its own instruction and synastry is second person plural, so both are exempt, and a caller that does not pass `{ frame }` gets no finding, because the two legitimate registers cannot be told from the prose alone. `scanSectionRules`/`summariseRuleScan` take an optional `RuleScanOptions` for this; the eval harness passes the frame. ⚠ As of v10.34 it is no longer *only* a measuring instrument: `antithesisTicExceeded` is exported from here and the quality gate clamps `voice_quality` on it, so this module's `antithesis-tic` regexes now decide what the pipeline repairs and caches. The remaining rules are still report-only. It is **pure, never throws, and makes no model calls** — microseconds per section — so unlike the LLM gate it *could* run on the hot path. ⚠ **As of v10.40 its `hard` findings are enforced**: `gateForCache` clamps `voice_quality` TO `MIN_INDIVIDUAL` when any of them fires and prepends a `STATED-RULE BREACH` critique naming each rule, its line and its repair. Clamped TO the bar rather than below it, because this module carries far more rules than `reading-fact-check.ts` and its production false-positive rate is unmeasured; the fact check, with 0 false positives across 84 sections, gets the harder clamp. `doctrine` and `soft` findings remain report-only — DOCTRINE.md is explicit that the grep finds candidates and THE LAW decides, and a soft finding is a breach only in aggregate.
- **`lib/reading-fact-check.ts`** (v10.38): deterministic numeric fact-checking of generated prose against the chart context the model was actually given. **Why it exists:** the v10.37 eval run shipped "Venus sits in Scorpio, in detriment, half a degree from your Sun and Pluto" — Venus was **18.7°** from the Sun, and the half-degree pair in that chart is Sun–Pluto. The model took a real fact and reassigned it. `chart_evidence` scored that section 3–4, `reading-rule-scan.ts` structurally could not see it (it is not a string pattern), and the claim reached the reader as confident, specific and false. That is the worst failure class the product has — FACT DISCIPLINE exists to prevent exactly it — and it is also, unlike prose quality, fully checkable, because the context block states every degree and orb the section is entitled to use. `checkNumericFacts(text, chartContext)` returns `FactFinding[]` with two checks: **`unstated-degree`** (`hard`) — a degree figure in the prose that the context does not state, within a rounding tolerance, so either invented or miscopied; and **`unsupported-closeness`** (`soft`) — a worded sub-degree claim ("half a degree", "exactly conjunct", "partile") where no aspect among the bodies named in that same sentence is within 1.5°. A third check, **`exemplar-bleed`** (`hard`, v10.40), closes the measurement gap v10.37 shipped knowingly: adding `SCENE_EXEMPLAR` fixed the scene requirement and introduced a fact-contamination risk guarded only by a prose warning, which this file recorded as "an eval question" — and an eval question with no instrument stays open forever. The exemplar's chart is a compile-time set, so `EXEMPLAR_PLACEMENTS` pins it (Mercury in Aries, Mars in Aquarius) and `checkExemplarBleed` reports a hard finding when a section asserts one of those pairs against a chart whose context does not carry it. It is kept as an explicit constant rather than parsed out of `SCENE_EXEMPLAR`, so rewriting the exemplar fails a test instead of silently switching the check off. Two scoping details are load-bearing: it runs on the WHOLE text, headings included (unlike the numeric checks, which use `proseOnly`), because the sub-header the exemplar models is a bled placement's likeliest home; and it is scoped to a SENTENCE, not a line — across a line the 24-character proximity window reaches over a full stop, and "your Mercury works in private. The Aries emphasis belongs to Mars" put the two 23 characters apart in unrelated sentences and read as a placement claim. `formatFactCheckLog` emits one `[AXIS_FACTS] section=… hard=… soft=…` line in the `[AXIS_*]` family. ⚠ **Calibrated against 84 real sections** (four gated runs of control-chicago-1987, contexts rebuilt per section): 0 hard, 1 soft — the genuine Venus error and nothing else. Two precision rules came out of that replay and are pinned: closeness needs **two** named bodies, because closeness is a relation, and `to the degree` is NOT in the pattern because it is the intensifier ("fixed to the degree") or the idiom ("to the degree that…"). As with the rule scan, **false positives are the design constraint** — a checker that flags correct prose about someone's own chart costs trust in every other line it reports. It checks numbers, not claims: it cannot tell whether an aspect was interpreted correctly, only whether the figure attached to it exists. Pure, never throws, no model calls. ⚠ **As of v10.40 it is no longer only a measuring instrument**: `gateForCache` clamps `chart_evidence` below the pass bar on a `hard` finding (see reading-quality-gate.ts), so this module decides what the pipeline repairs and caches. The eval harness still reports `facts_hard`/`facts_soft` and `facts_by_check` per section, plus a `facts` block in `summary.json` whose headlines are `sections_with_fact_error` and `sections_with_exemplar_bleed` — broken out per check because the two answer different questions: `unstated-degree` measures whether the model invents figures, `exemplar-bleed` whether PART 1's worked example contaminates readings about other people.
- **`lib/reading-preflight.ts`** (v10.41): the deterministic checks run on the HOT PATH, with at most one targeted regeneration — the module that makes the first version the reader gets the checked version. `preflightSection({ text, chartContext, section, planetSection, band })` returns `{ findings, instruction }`; `pickBetter` decides which attempt to serve; `formatPreflightLog` emits the `[AXIS_PREFLIGHT]` line. Pure, never throws, no model calls. The antithesis tic is reported once, from the tic check, with the rule scan's duplicate filtered out. Two bugs its tests caught before it shipped and which are now pinned: the rewrite was reserved through the gate's `gateCalls` counter, whose remainder is recorded again at the end of `after()`, **billing the call twice** against the daily cap; and an empty or failed rewrite has **no findings**, so it won `pickBetter` outright and the reader would have been served nothing at all — guarded in `pickBetter` and again in the route. See `/api/reading` above for the latency tradeoff this buys the quality with.

One fact, one home. Before editing a doc, put the change in the file that owns it:

|---|---|---|
| `CLAUDE.md` | Everything about how the code works (this file) | Claude Code (auto-loaded); hosts the `next dev` agent-rules block |
| `AGENTS.md` | Nothing — a pointer stub to this file | Codex and other `AGENTS.md`-reading agents |

Why `AGENTS.md` is a stub and not a symlink or a generated copy: Kay works from a Windows checkout, where git checks a symlink out as a plain text file unless symlinks are enabled, so Codex would read a file containing only `CLAUDE.md` and an edit to it would silently overwrite the link. A generated copy would put back the duplicate that drifted, and nothing would stop an agent hand-editing it. The `nextjs-agent-rules` block stays **only** in this file: `next dev` (`node_modules/next/dist/server/lib/generate-agent-files.js`) is a no-op while either file holds the current block, and when the block changes it rewrites it in `AGENTS.md` only if `AGENTS.md` already holds the markers *or* this file does not — so keeping the markers out of the stub keeps future upserts landing here.
