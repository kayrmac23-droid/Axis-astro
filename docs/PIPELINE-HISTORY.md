```bash
npm run build    # Production build

npm run lint     # ESLint (eslint.config.mjs)

npm run test:smoke  # Live reading-pipeline smoke test — real API call, real spend; see Tests below

npm run rescore -- --audit   # Rater bench, NO API: which pinned low scores are deterministic clamps
npm run openers              # Cross-chart opener diversity: generate ONE section for several charts and
                             # measure how much their opening paragraphs overlap. The only instrument that
                             # compares two CHARTS — every other check is scoped to one section of one
                             # reading. Use it before/after a change to an opener instruction.
npm run rescore              # Re-score the 21 frozen sections in fixtures/rater-bench/ (evaluator calls only,
                             # no generation). The prose cannot vary, so any movement is the EVALUATOR. Use it
                             # to test an EVAL_SYSTEM_PROMPT change before touching prompts.ts.
                             # --repeats=2 gives the run-to-run noise floor; read no diff without it.
```

## Architecture

Next.js 16 App Router, TypeScript.

**Data flow:** `BirthForm` → `/api/geocode` + `/api/timezone` → `/api/calculate` → `DualChartData` → the dossier (`DossierHeader` + `FrameControl` + `FrameShiftWheel` + `ReadoutRail` + `ReadingPanel`) → `/api/reading` (sequential streaming, one per planet section). Synastry adds a parallel flow: two births → `/api/synastry` → inter-aspects + composite → `SynastryAspectsPanel` + `SynastryReadingPanel`.

Page routes: `/` (main app), `/method`, `/guides`, `/sample`, `/synastry`.

### API routes

- **`/api/calculate`** (`maxDuration=30`): validates birth data (16 KB payload guard), rate-limited (30 req/60s), derives DST-accurate UTC offset via `Intl.DateTimeFormat`, fetches Pluto from JPL Horizons **only for a birth outside 1885–2099** (`plutoNeedsJpl` in astro-calc.ts — the span where the local Meeus series is valid; inside it Meeus agrees with DE440 to ~2″, outside it drifts to 20′ by 1850), 5s timeout, falling back to local Meeus; calls `calculateDualChart()`. `/api/synastry` applies the same rule per person; `pluto-source.test.ts` pins it. Returns `DualChartData` with `plutoSource`.
- **`/api/synastry`** (`maxDuration=30`): rate-limited (20 req/60s, 16 KB guard), computes two natal charts, inter-aspects, and a midpoint composite chart via `synastry-calc.ts`.
- **`/api/geocode`**: Nominatim proxy. 200-char query limit, rate-limited (30 req/60s per IP), one app-wide 1 req/s gate to Nominatim (`axis:rl:nominatim:global`), results cached in Redis for 30 days, field-whitelisted. Nominatim's usage policy forbids autocomplete, so `BirthForm` searches only on Enter or its SEARCH button — never on a keystroke timer.
- **`/api/timezone`**: GET `?lat=&lon=` → `{ tzName }`. Uses `tz-lookup` (offline, no external calls). Rate-limited (60 req/60s).
- **`/api/reading`** (`maxDuration=120`): ⚠ **DAILY QUOTAS (H1 abuse fix).** With only the per-minute limit in front of the site-wide daily cap, one script looping over random birth data exhausted the cap — refusing every reader for the rest of the day — from a single IP in ~25 minutes. Uncached requests now also pass a per-chart quota (`AXIS_READING_DAILY_PER_CHART`, default 40; the chart fingerprint ignores the client's Pluto hint, and the cap matters because skipping sections changes the prior digest and so mints new cache keys) and a per-IP quota (`AXIS_READING_DAILY_PER_IP`, default 120), both via `consumeDailyQuota` in `route-rate-limiter.ts`, after the per-minute limit and before the global budget, failing open without Redis. `getClientIp` buckets IPv6 by `/64` (`clientBucket`), since one subscriber holds 2^64 addresses and full-address keying made every per-IP limit decorative. Refusals carry `X-Axis-Quota: chart|ip` (429), and the global cap now carries `X-Axis-Quota: global` (503); the panels' `quotaFailure` (`reading-stream.ts`) turns either into a fatal unwind instead of failing ~21 sections in turn. Pinned in `reading-route-quota.test.ts`. Not done, deliberately: a signed chart token from `/api/calculate` stops nothing without a bot check there, since a script just fetches tokens — it belongs with Vercel BotID as one change. ⚠ **v10.47 — BUFFER ⇔ A CHECK RUNS.** A section is buffered only when something inspects it before the reader sees it (the pre-flight, or the inline gate on a non-opening section); otherwise it streams token by token. v10.41 made buffering unconditional and turning the pre-flight off by default never undid it, so every reader waited 15–25s per section for a check that no longer ran. The route sends `X-Axis-Delivery: stream|buffered`, and `ReadingPanel` shows its "checked before you see it" note only on `buffered`. Pinned in `reading-route-preflight.test.ts` and `reading-route-inline-gate.test.ts`. ⚠ **v10.41 — the section is BUFFERED and deterministically pre-flighted before the reader sees a character of it** (`lib/reading-preflight.ts`). The gate runs under `after()`, which is right for the LLM evaluator and wrong for everything else, and it produced the product's oddest property: the FIRST reader of an uncached section got ungated prose and every reader after them got the better text, so first impressions landed on the worst version the pipeline makes. Synchronous gating was measured and rejected (`scripts/time-gate.test.ts`) — generate + evaluate + repair does not fit `maxDuration` and an overrun costs the reader the section entirely. But the gate is two things wearing one name: the evaluator is slow, expensive and nondeterministic, while `scoreLength`, `detectBannedOpeners`, `antithesisVerdict`, `detectRescuePhrasings`, `scanSectionRules` and `checkNumericFacts` are pure, make no model calls and run in microseconds — `reading-rule-scan.ts` had said so in its own header the whole time ("unlike the LLM gate it *could* run on the hot path"). So the route generates, buffers, runs every deterministic check, and on a **hard** finding regenerates ONCE with the faults named, serving whichever attempt has strictly fewer findings (`pickBetter`; a tie keeps the first pass, which was written without a correction hanging over it). Cost: one extra generation **only on the sections that trip**, versus the evaluator's one call on every section whether it trips or not. Only a hard length miss regenerates — merely out-of-band scores 3 and the gate does not fail it either, so chasing it would spend a call for nothing. Truncated output is excluded, since regenerating hits the same token ceiling. The rewrite turn carries the faults and **not** the failed draft, which is the v10.40 repair lesson applied: the faults are string facts, so naming them is the whole message. ⚠ **THE TRADEOFF**: the section no longer streams token-by-token — roughly 15–25s of blank where tokens used to appear. It is affordable for every section but the first, because `ReadingPanel` fires the whole chain as fast as the API serves it (~5–9 minutes of generation against ~36 minutes of reading), so the pipeline runs minutes ahead of the reader; the opening section has no such cover and pays it in full, which is why `ReadingPanel` states plainly that each section is written in full and checked before it is shown. ⚠ **It is OFF by default** (`AXIS_PREFLIGHT_ENABLED=true` to enable), on the evidence of the 2026-11-07 gated run of control-chicago-1987. The checks are free, but running them requires buffering, and buffering costs every reader token-by-token streaming: a price paid on 100% of sections for a measured catch rate of **3 of 21** (four hard findings, all `prediction`; `detectBannedOpeners`, `detectRescuePhrasings` and every fact check scored zero). The same run showed where the prose actually fails — `specificity` 2.43 with 12 of 21 below the bar, `voice_quality` 2.57 with 9 below, a **5% first-pass pass rate** — and none of that is a string fact, so no deterministic check can reach it. The machinery is kept rather than deleted because the catch rate is one chart's and it is already built and tested: the flag turns it on without a redeploy once a wider sample, or a prompt fix that leaves deterministic breaches as the residue, justifies the buffering. ⚠ **`AXIS_INLINE_GATE=true` (default OFF) additionally gates a NON-OPENING section inline**, so the repair reaches the first reader too, paid out of the time they spend on earlier sections; it serves exactly what it caches, and `gatedInline` stops `after()` paying for the same evaluation twice. **It should stay off until `maxDuration` is raised**: worst case inline is generate + pre-flight rewrite + evaluate + repair + re-score ≈ 135s against a 120s ceiling, and an overrun costs the reader the whole section — strictly worse than today's failure mode, which is merely ungated prose. `INLINE_GATE_DEADLINE_MS` (35s from the top of the handler) makes it degrade safely rather than make it fit: with no budget, on an error, or on a verdict with nothing to cache, the first pass is served and `after()` runs the gate exactly as before. `[AXIS_PREFLIGHT]` and `[AXIS_INLINE_GATE]` log one line each in the `[AXIS_*]` family, and `preflight-rewrite` is a `ModelCallKind` so the extra generation shows in `[AXIS_USAGE]`. ⚠ `[AXIS_LEN]` measures the word count the GENERATOR produced, captured before the inline gate can replace the text. Rate-limited (20 req/60s, Redis-backed), validates section/planetSection against allow-lists, recomputes chart server-side from birth data (no client-trusted positions), checks Redis cache, calls `buildInterpretationContext()` + `formatEliteChartBlock()`, renders the section instruction through `renderSectionInstruction()` (which substitutes the length clause from the band *this chart* will be scored against — see prompts.ts), and streams the Claude response straight through to close. A mid-stream generation failure is classified and reported in-band via `reading-stream.ts` (see below), never as a status code — the response headers are already sent by then. Generation model: `claude-sonnet-5`. Quality evaluation uses `claude-sonnet-5-5` (exported as `EVAL_MODEL`); repair and doctrine-repair run on the caller's generation model, Sonnet 5. **Sonnet 5 / Opus 5 REMOVED the sampling params — sending `temperature` (or `top_p`/`top_k`) returns a 400 and fails the call, so there is no temperature knob (`AXIS_READING_TEMPERATURE` is gone); do not re-add one.** ⚠ As of v10.30 the thinking config is **no longer uniform**. The generation and repair calls still pass `thinking: { type: 'disabled' }` — these models otherwise default to adaptive thinking, whose tokens count against `max_tokens` (truncating the per-section prose budget) and add first-token latency across the ~21 sequential sections, and a repair is a constrained rewrite against an explicit critique rather than a judgment call. The **evaluator** passes `thinking: { type: 'adaptive' }` with `output_config: { effort: 'medium' }` and `EVAL_MAX_TOKENS` raised 1200 → 4000 (adaptive thinking tokens come out of `max_tokens`, so a JSON-only budget would truncate the scores object the moment the model thought at all). Why the evaluator is the exception: it runs under `after()`, entirely off the response path, so reasoning costs the reader no latency — the latency argument that justifies no-thinking on the generator does not apply to it at all — while scoring nine prose criteria and emitting strict JSON is precisely the task reasoning helps most. The former pairing (Opus 5 with thinking disabled) was the worst of both: Opus input bills at 2.5× Sonnet over roughly the SAME token volume the generation call pays, making **evaluation the larger half of the bill** for a benefit the first reader never sees, while the judgment it was bought for was switched off. Note `thinking: {type:'disabled'}` is a **400** on `claude-sonnet-5-5`, so the split is enforced by the API, not just by preference. **When birth time is unknown, the dedicated `ascendant`/`lagna` section is not sent to the model at all** — the angle is uniform across the zodiac at noon, so the route returns a short deterministic explainer instead (free; no model call, no rate-limit spend); every other section still runs, since sign-based placements are accurate without a birth time. **The LLM quality gate runs as evaluate-and-recache**: the stream closes first, then `gateForCache()` runs via `after()` (from `next/server`) while the invocation is still alive, so gating adds **zero latency to the reader** — `after()` (not bare post-`close()` code) is what guarantees the platform keeps the instance alive to finish it, so the cache write and the spend count are not dropped when the response flushes and decides only what lands in the cache. Consequence to keep in mind: the *first* reader of an uncached section sees ungated first-pass prose; every reader after them is served the gated (and where it failed, repaired) text. Every gate call carries a request timeout that expires at `GATE_HARD_DEADLINE_MS` (112s from the top of the handler) with SDK retries off, so a slow call cannot run past `maxDuration`; and each call is recorded against the daily cap the moment it is made (`gateForCache`'s `onModelCall`), with any remainder recorded at the end — recording only a final total lost every call made before an overrunning invocation was killed. When the gate cannot confirm a section (repair failed its re-score, repair errored or came back unusable, no budget left to repair — and, since v10.47, the evaluator errored on the first pass, or a repair could not be re-scored because the re-score errored or ran out of budget) it returns `provisionalText` — the doctrine-clean first pass, or the unscored repair where one exists — and the route caches it for `PROVISIONAL_TTL_SECONDS` (24h) instead of not at all: uncached, every later view of the chart regenerated and re-gated it at ~4 calls per view, indefinitely. Truncated or doctrine-breaching text is never cached, provisionally or otherwise. Cost per uncached section is 1 model call (generate) + 1 (evaluate), + 1 more when only a doctrine hit fails (the 500-token surgical edit, not re-scored), or + 2 more when a full repair fires (the repair itself + a re-score of the repair) — all counted through `recordModelCalls` against the daily cap. The generation call is **reserved as it is made** (the write is fired, deliberately NOT awaited — it is the reader's critical path — and flushed under `after()` on both the success and the failure exit); only the gate's calls are recorded from inside `after()`. Recording the whole count post-gate left the counter trailing real spend by the full gate duration (~30–60s), so concurrent traffic could run past the cap by the number of requests in flight, and a generation that failed after billing went uncounted entirely. The counter now bounds calls *started*, which is what the cap is for; a reservation is never refunded (`reading-route-budget.test.ts`). **Per full reading**, with every section uncached: a natal reading is 21 sections (9 Tropical + 8 Sidereal + 4 Divergence; 19 when birth time is unknown, since `ascendant`/`lagna` are free), so **42 calls minimum** (generate + evaluate on every section) and **up to 84** if every section takes a full repair; synastry is 6 sections, 12–24 calls. The call COUNT is unchanged by v10.30; what changed is the price of the evaluate/recheck half of it (Opus 5 → Sonnet 5.5, $5/$25 → $2/$10 per MTok) and the volume every call carries (the v10.30 length reset cut the natal reading ~28%, and because prior sections are resent verbatim on every later section, each word cut is a word removed from up to twenty subsequent prompts on BOTH the generation and the evaluation call — ⚠ **v10.36 reversed that cut**, for the reasons under *Per-section-type targets* below, so the volume term is back to roughly its pre-v10.30 level; the compounding mechanism this describes is unchanged and is why length is still the cost term to watch). A cache hit costs 0 calls, and `AXIS_GATE_ENABLED=false` drops a section to 1. The real per-reading figure, with token counts and list-price cost, comes from the `[AXIS_USAGE]` lines or `npm run eval`'s `summary.json` — no repair rate is assumed here. `AXIS_GATE_ENABLED=false` disables gating without a redeploy (mirrors `AXIS_READINGS_ENABLED`), falling back to caching only a clean, non-truncated first pass. Wall-clock guards in `gateForCache` measure from the top of the handler: no eval starts after 95s elapsed, no repair after 70s — overrunning costs the cache write, never the reader's section. Cache-write guards are the `truncated` stop_reason flag, `isTruncated()`, and the deterministic banned-phrase scan (`detectBannedPhrasings`, now in `reading-quality-gate.ts`). The scan runs in two passes: **literal** (`BANNED_HIERARCHY_PHRASINGS` + `BANNED_RESCUE_PHRASINGS`, substring-matched — every entry is a construction with no innocent use) and **contextual** (`detectContextualHierarchy`, for ordinary words like "underneath"/"beneath"/"the mask" that only breach THE LAW within `HIERARCHY_PROXIMITY_CHARS` of identity/system language). Keep bare ordinary words OUT of the literal list — a false positive now sends a clean section through a needless repair pass. A doctrine hit is no longer a bare cache veto. When the evaluator otherwise approves the section, the gate sends only the offending sentence(s) through a 500-token surgical edit and splices the replacements into the original byte-for-byte; this avoids paying for or risking regression across a full-section rewrite. If the prose rubric also fails, the ordinary full repair still addresses both failures. Gate outcomes log one greppable `[AXIS_GATE] section=… reason=… <per-criterion scores>` line per gated section — the only production visibility into the score distribution. Every model call the route makes — the generation and each gate call — logs one `[AXIS_USAGE] section=… call=generate|evaluate|recheck|repair|doctrine-repair model=… in=… cache_read=… cache_write=… out=… stop=…` line (`lib/usage-log.ts`) from the API's own `usage`; the generation line adds `prior=<sections already read>`. It is the only production record of what a reading costs and whether prompt caching is landing (a section after the first should show a large `cache_read` and a small `in`).

Planet sections — **tropical**: sun, moon, ascendant, mercury, venus, mars, jupiter_saturn, key_aspects, rahu_ketu · **sidereal**: lagna, sun, moon, mercury, venus, mars, jupiter_saturn, rahu_ketu · **synthesis** (The Divergence): agree, diverge, tension, closing · **synastry**: luminaries, venus_mars, outer_planets, composite_chart, central_dynamic, navigation

### Core libs

- **`lib/astro-calc.ts`**: VSOP87B (planets), VSOP87+nutation (Sun), ELP2000 (Moon) via `astronomia`. ⚠ **Planets are evaluated in TT, angles in UT** (v10.47): `toJde` adds ΔT (`astronomia/deltat`, NASA model + observed IERS table) before every position call, while RAMC/ASC/MC stay on the UT Julian Day because they follow Earth's rotation. Until then everything ran at UT and the Moon trailed JPL by exactly the distance it moves in ΔT (31″ in 1987, 36″ in 2024); now Sun ≤ 0.1″ and Moon ≤ 4.1″, pinned against JPL reference values in `astro-calc.test.ts`. Not a `READING_PROMPT_VERSION` bump: positions moved by under an arcminute, and cold-starting the whole cache is not worth it. Meeus Ch.37 for Pluto — ⚠ `astronomia/pluto.heliocentric()` is in the J2000 frame, so the geocentric subtraction uses Earth's `position2000()` and only the result is precessed to date (plus light-time, nutation, aberration). Mixing frames, as the code did until v10.33, drifted ~50″/yr from 2000 (+57′ in 1930); now < 0.03′ vs DE440, pinned in `astro-calc.test.ts`. True node via `moonposition.trueNode` (all five Meeus terms). Lahiri ayanamsa (~23.85° at J2000; the formula lives in client-safe `lib/ayanamsa.ts` so the computation interstitial shows the cast chart's offset from the same source). Whole Sign houses. Exports `calculateDualChart(BirthData, overrides?)` → `DualChartData`.
- **`lib/interpretation-engine.ts` — `buildDivergencePlan(DualChartData)`**: the single deterministic evidence base for all four Divergence sections (`formatSynthesisBlock` renders it; the route sends NOTHING else for `synthesis`, so a fact absent from the plan is a fact the model does not have). Walks all twelve bodies plus both angles in both frames, carrying degree, dignity, retrogradation, sidereal nakshatra and sign-ruler condition. **Concordance has two grades** — full (sign + dignity + house) and SAME-SIGN (sign + dignity, house moves). The second grade is load-bearing, not a technicality: AXIS uses Whole Sign houses, so when the Ascendant shifts sign under the ayanamsa — which it does on most charts — every same-sign body ALSO renumbers house. Requiring the house to match made concordance structurally unreachable and left the `agree` section with no allocated evidence on ~75% of charts. Divergences are ranked by `structural` (size of the shift: sign 4, dignity 3, house 2, Ascendant 9 because a Lagna shift renumbers every house) plus `DIVERGENCE_BODY_WEIGHT` (luminaries and angles > personal planets and the nodes > outers) — the ranking rule that used to be prose in the diverge prompt, moved here because ranking from chart facts is deterministic and a prompt-side instruction cannot be verified. Candidates at or above `STRUCTURAL_CUTOFF` are worked in depth (max 4, **no minimum** — the chart decides); the rest land in `remaining`, which the diverge prompt names in one compressed clause as THE LAW requires. ⚠ `SIGN_RULERS_VEDIC` is a copy of `SIGN_RULERS_TRADITIONAL`, so the sign ruler is NEVER system-specific — a changed ruler is a consequence of the changed sign and must not be scored or described as the systems disagreeing about rulership. What IS independent evidence is the dispositor's own *condition* differing.
- **`lib/synastry-calc.ts`**: computes inter-chart aspects (orb-limited, 5 major aspects) between two natal charts and a midpoint composite chart. When either birth time is unknown, `formatSynastryBlock` opens with the same `⚠ BIRTH TIME UNKNOWN` notice the natal context uses (so SHARED_RULES' BIRTH TIME UNCERTAINTY fires) and withholds that person's Ascendant, MC and house numbers, plus the composite's; the route also skips the composite elite chart block in that case (`synastryTimeUnknown`).
- **`lib/interpretation-engine.ts`**: derives astrological facts from chart data; formats structured context injected into every reading request. `computeAscendantAspects(ascendant, planets)` supplies aspects to the Ascendant/Lagna — the angle is not in `chart.planets`, so `computeAspects()` never sees it and that section previously carried no aspects at all while the prompt demanded the model work "every major aspect". Angle orb is 5° (tighter than the 8° planetary orb: an angle is a point, and the ASC moves ~1° per four minutes of birth time). The block always renders, stating explicitly when nothing is within orb, so the model is never left to infer aspects it wasn't given. **Tropical only**: Western degree aspects are frame-invariant, so the Sidereal frame no longer receives them (they made every Sidereal section re-walk the Tropical aspects). Sidereal planet and Lagna blocks instead carry Jyotish evidence: `jyotishSignStatus` (exalted/moolatrikona/own/friend's/neutral/enemy's/debilitated by Parashara's natural friendships), `lordshipsOf` (houses ruled from the Lagna, plus a full HOUSE LORDS table on the Lagna), whole-sign graha drishti (`drishtiHouses`; Mars 4/8, Jupiter 5/9, Saturn 3/10, nodes none) and same-sign conjunction under `GRAHA RELATIONSHIPS RECEIVED` (bulleted, so `countAspectsInContext` scales Sidereal bands from it), `neechaBhangaConditions` (classical cancellation checks from Lagna and Moon, reported as conditions met, never a verdict), and a `FRAME SHIFT` line stating the shift as backward and whether the house moved. No placement carries a within-system boundary flag (DOCTRINE.md: SIGN-BOUNDARY CUSPS — DEREGISTERED; `cuspNeighbour` is geometry only). The Divergence plan notes a body that is within 3° of a boundary in one frame and away from one in the other, the cross-system observation the ruling retains; every aspect carries an orb class (`orbTier`: tight ≤2°, close ≤4°, moderate ≤6°, wide >6°); a planet under a quarter of its typical speed is marked `NEAR STATION` and its applying aspects are labelled may-never-perfect (`isNearStation`). The key-aspects context names the TIGHTEST ASPECT IN THE CHART and, given the reading so far (`options.priorText`), marks each aspect ALREADY WORKED / NOT YET WORKED (`aspectAlreadyWorked`). `detectMajorYogas` reports Harsha/Sarala/Vimala individually (one dusthana lord in a dusthana each forms a Viparita Raja Yoga; the old check demanded two). The dasha block (`formatDashaBlock`) gives antardasha start and end and a `⚠ TRANSITION` note within 60 days of a boundary. **Unknown birth time** (v10.33): `computeVimshottariDasha` returns null (the noon Moon can sit ~6° off, which moves the timeline by years), so no section and no cache key carries a dasha; Lagna-derived yogas are not computed for the Sidereal sections or the Divergence plan; house lordships and Lagna-referenced neecha-bhanga conditions are withheld; the Tropical cross-chart note compares signs only. Western `DIGNITIES` covers the seven traditional planets only — the nodes have no Western dignity. Raja yoga pairs are reported once, not once per lord order. Data-driven via `PLANET_CORE`, `SIGN_DATA`, `HOUSE_DATA`, `DIGNITIES`, `NAKSHATRA_DATA` constants.   **The structural cause**: six of the nine 5 anchors were universally quantified over the whole section — "every substantive claim", "every strength", "every subsection", "every characterisation", "every major claim", "nothing performs depth", "no construction repeats" — and every 4 anchor permitted exactly one defect. A universally quantified property of a 1000-word section is falsified by one counter-example anywhere in it, so the top of the scale was unreachable and the 4 tier nearly so. Scoring is an ordered procedure (run the **AWARD TEST**, then the fault list, then score from what was found) rather than a fault list with an exhortation on top; each criterion gains an AWARD TEST naming a findable feature, so the rubric finally has a procedure for *awarding* and not only for deducting. A per-criterion **`evidence`** entry is required **at every point on the scale**: a one-sided audit obligation creates a floor exactly where it starts, which is the mechanism that pinned `falsifiability` at 3 while the rubric asked for an inversion only below 3. A 3 now costs a named absence, and "adequate"/"could be stronger" are ruled out as absences. `GateResult` carries `llmScores` (pre-clamp) and `evidence` so a rubric change is measured against what the rater *said*, not against a number a clamp had already set. - **`lib/reading-thread.ts`** + **`lib/reading-order.ts`**: the reading thread that makes a natal reading one continuous document. `reading-order.ts` (client-safe) holds `NATAL_SECTION_ORDER` and `priorSectionsFor` — every section the reader has read before a given one (all of each earlier frame, then this frame's earlier sections). `ReadingPanel` opens a thread per cast chart (a UUID `threadId` in every `/api/reading` body); the route loads the earlier sections (`loadPriorSections`), sends them as one content block per section ahead of the chart context (identical blocks across requests, cache breakpoint on the last, so prompt caching reuses all but the newest), and stores this section's text (`storeThreadSection`) **before** closing the stream, because the client fires the next section the instant this one ends. Stored text is what the reader saw (first pass, cached text, or the unknown-time notice), never the gate's later repair. The server holds the text, never the client: the 16 KB payload guard would reject it by the fifth section, and client-supplied text would be a prompt-injection and cache-poisoning path. The thread key binds the id to the chart's birth data; entries expire after 24h (Redis, with a per-instance in-memory fallback). `priorDigest` is folded into the reading cache key, and as of v10.29 it digests **which** earlier sections preceded this one, in order — deliberately not their prose; an unthreaded request is an opening section. It used to digest the text, which quietly destroyed the cache: the route threads the FIRST PASS (continuity is with what was read) while the gate caches the REPAIRED text, so the next reader of the same chart was served `T1′`, threaded `T1′`, and computed a different key for section 2 than section 2 was cached under. The chain forked at the first repaired section and never rejoined — reusable only for the maximal prefix of sections the gate did not repair (expected `(1-r)/r` of 21 at repair rate `r`; about 4 at r=0.2), with every later section regenerated for every reader forever, including the same person reloading their own dossier, and every miss writing a row under a digest nobody would ever produce again. Keyed on the section list, every reader of a chart computes the same key at every section. What is given up: a cached section may have followed the first-pass wording of an earlier section while this reader saw the repaired wording — a repair of the same section, not a different one. A section the thread is missing (failed, expired) is absent from the list and so changes the digest, which is correct: that reading genuinely had different material before it. The gate gets the same prior blocks (`priorSectionBlocks`, not a flattened string) so its evaluator and repair calls read the reading so far from the prompt cache; its evaluator scores repetition across the reading. Synastry is not threaded. `phrasesAlreadyUsed` / `overusedTics` (rendered by `phrasesAlreadyUsedBlock`, placed ahead of the section instruction) name the refrains the reading so far already leans on — 2–4-word phrases repeated ≥3 times across ≥2 sections, headings and chart vocabulary excluded, plus counted verbal tics such as the "rather than" antithesis — so the next section is told by name not to reuse them. ONE CONTINUOUS READING also bans contradicting an earlier behavioural claim without naming the condition under which each holds.
- **`lib/reading-stream.ts`**: both halves of `/api/reading`'s in-band failure protocol, kept in one file so they cannot drift. A generation failure cannot be an HTTP status — by the time the model call fails the streaming `Response` has already gone out with a 200 — so the route writes a sentinel into the body instead. `classifyGenerationError(err)` (server) splits failures into **fatal** (the *account* is the problem: an exhausted credit balance, which Anthropic reports as a **400 `invalid_request_error`** and not a 402, so the message must be read and not just the status; plus 401/403 auth) and **transient** (overload, 5xx, network). `detectStreamError(text)` (client) reads the sentinel back: `[AXIS_STREAM_ERROR: generation failed]` stays retryable, `[AXIS_STREAM_ERROR: unavailable:<code>]` is fatal and makes the panel throw `ReadingUnavailableError` to unwind the whole run. Why this exists: a natal chart fans out to ~21 sections and each panel retries once, so treating a fatal failure as retryable turns **one** exhausted balance into ~42 doomed API round trips while telling the reader "please retry" for something no retry can fix. An unknown future `unavailable:` code stays fatal by design. Server-side each failure logs one greppable `[AXIS_GEN_FAIL] section=… fatal=… code=…` line.
- **`lib/reading-rule-scan.ts`**: the deterministic compliance scan for the `SHARED_RULES`/`DOCTRINE.md` constraints that are pure string facts about finished prose. **Why it exists:** before v10.30 the pipeline had exactly five deterministic checks on generated prose (`scoreLength`, `isTruncated`, `detectRescuePhrasings`, `detectBannedOpeners`, `detectBannedPhrasings`); everything else was either advisory rubric prose handed to the LLM evaluator or unchecked. That left the rules whose violations a reader notices *immediately* and which are trivially checkable in code with **zero enforcement anywhere** — no prescriptions ("you should", "work on"), no predictions ("you will", "this will bring"), British spelling, no bullet points, 3–4-sentence paragraphs, no greetings/sign-offs, and THE SMOKE DETECTOR word list against generated prose. The engineering budget had gone to an LLM judge for the hard, subjective 20% while the trivially automatable 80% was guarded only by a prohibition ~11,000 tokens upstream of the output. `scanSectionRules(text)` returns `RuleFinding[]` (`rule`, `severity`, `match`, `line`); `summariseRuleScan` aggregates; `formatRuleScanLog` emits one `[AXIS_RULES] section=… hard=… doctrine=… soft=…` line in the `[AXIS_*]` family. Three severities: **`hard`** = unambiguous breach of a stated rule, **`doctrine`** = a THE SMOKE DETECTOR or claim-level LAW candidate (DOCTRINE is explicit that the grep finds candidates and THE LAW decides, so these are reported for audit, never asserted as failures), **`soft`** = a breach only in aggregate (one long paragraph is a slip, six is a pattern; `antithesis-tic` — added v10.31, re-scoped to density in v10.45 — reports ONE finding per section once "rather than" / "not X but Y" / "less a X than" falls too densely, carrying the measurement (`antithesisVerdict`: the worst paragraph, or the spread against a one-per-two-paragraphs allowance), and is scoped to keep bare "rather", concessions, "not only…but" and ordinary comparatives silent). ⚠ **False positives are the design constraint**, because a scanner that cries wolf gets switched off: prescriptions/predictions match only SECOND-PERSON constructions (bare "consider" and "will" are ordinary English — "the pattern will often surface" is the hedged form the prompt actually requires), the smoke-detector terms are sentence-scoped and fire only alongside inter-system language (so the conjunction's "Merger" and Scorpio's "merger through depth" stay silent), and British spelling uses a closed list of the exact pairs the prompt names rather than an `-ize`/`-our` heuristic (so "size", "prize", "glamour", "hour" are safe). ⚠ v10.38 narrowed the `prescription` check: "should"/"ought to" match anywhere, but "need to"/"must"/"have to" are ALSO ordinary descriptive English inside a clause introduced by a subordinating conjunction, and the v10.37 run reported "a conversation that gives you room to draft **before you have to speak**" as a hard breach. A temporal clause is not advice, and a hard breach is the loudest thing this file can say, so the conditional modals now carry a negative lookbehind for before/until/when/whenever/while/if/once/unless/after/as/where/than. ⚠ v10.48 narrowed `prediction` and `prescription` again, after the 2026-11-08 three-chart eval (v10.47's denser second person) took hard findings 6 → 13, nearly all false: "you will"/"you'll" and the conditional modals no longer match when a relative or subordinating word sits IMMEDIATELY before "you" ("something you will privately resent", "before you'll trust it", "something you have to locate"), and "should have" + past participle is treated as a counterfactual, not advice — adjacency is required so a fronted clause ("when this ends you will meet someone") stays a prediction, and bare "that" is deliberately not an introducer because the complementiser ("suggests that you will") is the prediction shape. ⚠ v10.35 added `register-drift` (`hasRegisterDrift`/`registerFor`), the PART 4 second-person check: a natal section containing NO second-person pronoun at all is `hard`. It is **frame-aware and fails closed** — The Divergence is third person by its own instruction and synastry is second person plural, so both are exempt, and a caller that does not pass `{ frame }` gets no finding, because the two legitimate registers cannot be told from the prose alone. `scanSectionRules`/`summariseRuleScan` take an optional `RuleScanOptions` for this; the eval harness passes the frame. ⚠ As of v10.34 it is no longer *only* a measuring instrument: `antithesisVerdict` is exported from here and the quality gate clamps `voice_quality` on it, so this module's `antithesis-tic` regexes and density rule now decide what the pipeline repairs and caches. The remaining rules are still report-only. It is **pure, never throws, and makes no model calls** — microseconds per section — so unlike the LLM gate it *could* run on the hot path. ⚠ **As of v10.40 its `hard` findings are enforced**: `gateForCache` clamps `voice_quality` TO `MIN_INDIVIDUAL` when any of them fires and prepends a `STATED-RULE BREACH` critique naming each rule, its line and its repair. Clamped TO the bar rather than below it, because this module carries far more rules than `reading-fact-check.ts` and its production false-positive rate is unmeasured; the fact check, with 0 false positives across 84 sections, gets the harder clamp. `doctrine` and `soft` findings remain report-only — DOCTRINE.md is explicit that the grep finds candidates and THE LAW decides, and a soft finding is a breach only in aggregate.
- **`lib/reading-fact-check.ts`** (v10.38): deterministic numeric fact-checking of generated prose against the chart context the model was actually given. **Why it exists:** the v10.37 eval run shipped "Venus sits in Scorpio, in detriment, half a degree from your Sun and Pluto" — Venus was **18.7°** from the Sun, and the half-degree pair in that chart is Sun–Pluto. The model took a real fact and reassigned it. `chart_evidence` scored that section 3–4, `reading-rule-scan.ts` structurally could not see it (it is not a string pattern), and the claim reached the reader as confident, specific and false. That is the worst failure class the product has — FACT DISCIPLINE exists to prevent exactly it — and it is also, unlike prose quality, fully checkable, because the context block states every degree and orb the section is entitled to use. `checkNumericFacts(text, chartContext)` returns `FactFinding[]` with two checks: **`unstated-degree`** (`hard`) — a degree figure in the prose that the context does not state, within a rounding tolerance, so either invented or miscopied; and **`unsupported-closeness`** (`soft`) — a worded sub-degree claim ("half a degree", "exactly conjunct", "partile") where no aspect among the bodies named in that same sentence is within 1.5°. A third check, **`exemplar-bleed`** (`hard`, v10.40), closes the measurement gap v10.37 shipped knowingly: adding `SCENE_EXEMPLAR` fixed the scene requirement and introduced a fact-contamination risk guarded only by a prose warning, which this file recorded as "an eval question" — and an eval question with no instrument stays open forever. The exemplar's chart is a compile-time set, so `EXEMPLAR_PLACEMENTS` pins it (Mercury in Aries, Mars in Aquarius) and `checkExemplarBleed` reports a hard finding when a section asserts one of those pairs against a chart whose context does not carry it. It is kept as an explicit constant rather than parsed out of `SCENE_EXEMPLAR`, so rewriting the exemplar fails a test instead of silently switching the check off. Two scoping details are load-bearing: it runs on the WHOLE text, headings included (unlike the numeric checks, which use `proseOnly`), because the sub-header the exemplar models is a bled placement's likeliest home; and it is scoped to a SENTENCE, not a line — across a line the 24-character proximity window reaches over a full stop, and "your Mercury works in private. The Aries emphasis belongs to Mars" put the two 23 characters apart in unrelated sentences and read as a placement claim. `formatFactCheckLog` emits one `[AXIS_FACTS] section=… hard=… soft=…` line in the `[AXIS_*]` family. ⚠ **Calibrated against 84 real sections** (four gated runs of control-chicago-1987, contexts rebuilt per section): 0 hard, 1 soft — the genuine Venus error and nothing else. Two precision rules came out of that replay and are pinned: closeness needs **two** named bodies, because closeness is a relation, and `to the degree` is NOT in the pattern because it is the intensifier ("fixed to the degree") or the idiom ("to the degree that…"). As with the rule scan, **false positives are the design constraint** — a checker that flags correct prose about someone's own chart costs trust in every other line it reports. It checks numbers, not claims: it cannot tell whether an aspect was interpreted correctly, only whether the figure attached to it exists. Pure, never throws, no model calls. ⚠ **As of v10.40 it is no longer only a measuring instrument**: `gateForCache` clamps `chart_evidence` below the pass bar on a `hard` finding (see reading-quality-gate.ts), so this module decides what the pipeline repairs and caches.
